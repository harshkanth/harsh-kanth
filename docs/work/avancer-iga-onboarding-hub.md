## The challenge

Identity governance products have several distinct readers. IAM administrators install and configure the product, application owners respond to onboarding requests, and buyers need to understand the value before anyone installs anything. Each reader needs different documents, but all of them have to describe the same product in the same words.

The product also connects to several identity providers and AI services, each with its own prerequisites, and it was renamed partway through the project.

## How I approached it

### One product, several readers

I mapped each document to a single role and a single job. Admin content covers configuration and policy, owner content covers responding to requests, and the architecture document carries the technical depth that would otherwise clutter both. Cross-references connect them instead of repeating content.

### Prerequisites that remove guesswork

Integration setup is where onboarding usually stalls. Each discovery source and AI provider got its own prerequisites topic with the exact permissions, credentials, and settings to have ready, so an administrator can prepare everything before installation starts.

### A clean rename across the whole suite

When the product was renamed from IARP to IGA Application Onboarding Hub, I carried the change through every document, file name, and screenshot caption in one controlled pass, so no customer-facing material used two names.

### Documents generated, not hand-assembled

The suite is delivered as branded Word and PDF documents. I generate them programmatically from structured content, which keeps formatting, numbering, and callouts consistent across every guide and makes revisions repeatable rather than manual.

## What this shows

- Planning and delivering a complete documentation suite, not just a single guide
- Writing for technical administrators and for buyers in the same project
- Treating document production as an engineering problem when it saves time
