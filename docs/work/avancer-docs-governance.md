# Style guide and documentation governance

<p class="lead">Avancer's documentation spans several identity products, each with its own history and its own writers. I wrote the house style guide and then ran compliance passes that brought the documentation set to one consistent standard.</p>

## The challenge

When documentation grows product by product, every guide develops its own habits: different heading schemes, different words for the same action, different release note conventions. Customers notice, and it makes every new document slower to write because there is no agreed answer to basic questions.

## What I delivered

- **Avancer Style Guide v2.0**, covering tone and voice, how to address the reader, American English, parallel construction, procedure and troubleshooting structure, and release note conventions, comparable in scope to the Microsoft, Apple, and SAP style guides
- **A visual identity and callout system** for documents: heading hierarchy, colors, numbered sections at every level, and a consistent set of note, tip, and warning callouts
- **Compliance passes** across release notes, user guides, connector guides, an Oracle to SQL Server migration guide and playbook, a TLS configuration guide, and installation, admin, and user guides
- **A seven-document set for NELM**, a non-employee lifecycle management product: installation, configuration, development, and design documents, testing evidence, and a product brief
- **A Confluence Cloud space** for Identity Bridge, with branded PDF exports that match the Word templates

## How I approached it

### Decide once, apply everywhere

The style guide answers the questions writers ask most often, with a rule and an example for each. A few of the decisions:

| Topic | Rule |
|-------|------|
| Abbreviations | "for example" instead of "e.g.", "and so on" instead of "etc." |
| Lists | Oxford comma, parallel construction in every list |
| UI actions | "click" for buttons and links, "select" for options and values |
| Inclusive terms | "allowlist" and "blocklist" |
| Release notes | "Improved" instead of "Fixed", with a consistent structure per entry |
| Headings | Numbered at every level, so reviewers can reference any section precisely |

### Make compliance cheap

Rules only work when following them is easier than ignoring them. Templates carry the structure and styling, so writers start compliant, and review focuses on content rather than formatting.

### Fix the set, not just the file

Each compliance pass covered a group of related documents together, such as a release note, the migration guide it references, and the playbook that follows, so terminology and cross-references line up across the set.

## What this shows

- Setting documentation standards, not just following them
- Turning a style guide into templates and workflows that teams actually use
- Raising the quality of an existing documentation set without rewriting it from scratch
